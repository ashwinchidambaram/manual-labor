# Findings & Decisions

## Requirements (from SPEC.md + CLAUDE.md, 2026-10-28)
- Build "Manual Labor" (`manuallabor` package, `labor` CLI): document → KB zip (Markdown articles + images/ + manifest.json) with a human-in-the-loop review loop.
- v1 inputs: born-digital PDF, scanned PDF (OCR), DOCX. Out: HTML ingest, chat/retrieval, multi-tenant, KB adapters.
- Pipeline: ingest → parse (two parsers, always) → score → group → [HIL scope] → clean+attach → score → [HIL verify ⇄ agent pass] → assemble → export.
- Hard invariant: faithfulness. Cleanup is lossless normalization only; deterministic alignment check (§5.2) always runs; numbers never change silently.
- Priorities in order: faithfulness, reviewer time, portability (local Ollama/vLLM/llama.cpp or Anthropic/OpenAI-compatible APIs).
- 12 build modules (0–11) with gates; module N+1 may not start until N's gate is recorded in docs/PROGRESS.md with the proving command output.
- Subagent pattern per module: design → implement → review (fresh agent, not the implementer) → fix. UI modules add a Playwright UX-check agent.
- Orchestrator must itself run: `uv run pytest -q`, `uv run labor check ./tests/fixtures/project-a`, `--live` variant, `npm test`, `npm run e2e`.
- User direction (2026-10-28): use /planning-with-files; delegate to Opus / Sonnet / Haiku subagents with properly scoped briefs; real verification tests, not "should work".

## Resource constraint (user flagged 2026-10-28): 16 GB machine

- Rules from now on: the orchestrator does NOT run the full suite while an implementer is running it; slow tests (`-m slow`) run once at the gate; never dispatch two agents that both exercise Docling concurrently; one implementer per module unless their work is non-overlapping and light.

## Cross-cutting requirement: self-improvement from HIL feedback (user, 2026-10-29; "nice to have, not required")
Principle: every human action is a labelled example. Learned behaviour may change proposals, ranking, and confidence; it may never bypass or weaken the deterministic faithfulness check (CLAUDE.md invariant). All learning is per-project by default with an opt-in global store; nothing leaves the machine.
Slots, cheapest first:
- **M7 (state store)**: capture is the prerequisite. Store every decision as a full example: block id, raw_text, raw_text_by_parser, clean_text before/after the human edit, signals snapshot, score, threshold, action, flag category + note, figure re-attach choices, regrouping moves, agent-pass accept/edit/reject with the proposal. One table, append-only, exportable as JSONL. (SPEC §5.4 already requires part of this.)
- **M5 (cleanup)**: a `LearnedRules` hook read at cleanup time: (a) recurring human edits that are lossless by the §5.2 classes become deterministic rules for that project/doc family (e.g. a header remnant, a bullet glyph map, a de-hyphenation exception list); (b) approved (raw → clean) pairs become few-shot examples for the cleanup LLM prompt, nearest-neighbour by block type/signals. Both still go through faithfulness.
- **M3/M10 (scoring + calibration)**: beyond the threshold, fit per-signal reliability from decisions (which signals predict "edited"), suggest weight changes with evidence, never apply silently; learn OCR confusion pairs from human corrections (`3S`→`35`) into the `NumericVariant`/confusable table per document family; learn numeric-spec lexicon additions from flagged "wrong text" notes.
- **M4 (grouping)**: human regrouping moves become few-shot examples for topic naming/assignment and a per-project "do not merge" list.
- **M10 (agent pass)**: prior accepted/rejected proposals for similar flags are shown to the model as examples; rejected proposals' rationale is excluded from re-use.
- **UI (M8/M9)**: a "why did this change" chip when a learned rule or example influenced output, so the user can disable it.
Design docs for M5, M7, M10 must include a "Learning hooks" section; M7's schema is the only part that is mandatory now (capture everything; learning can be added later without migration).

### Learning must be reversible (user, 2026-10-29)
- **Baseline is immutable.** The shipped behaviour (deterministic rules, default signal weights, default threshold, empty few-shot store) is the baseline and is never edited in place by learning.
- **Learning mode is a toggle** in `ProjectConfig` (`learning.enabled`, default off until the baseline is validated; later default may flip). Off = baseline behaviour exactly, even if learned state exists on disk.
- **Learned state is a separate, versioned layer** (`<project>/learning/` with numbered snapshots + a `global/` opt-in store), applied on top of the baseline at runtime. Nothing learned is written into code, config defaults, or the decision store itself.
- **Reset button** = delete/disable the learned layer; decisions (the raw examples) are kept so learning can be re-derived later. Also a per-rule disable from the UI chip.
- **Rollback** = pick a previous snapshot; every scoring/cleanup output records which learning snapshot (or `baseline`) produced it, so a regression can be traced and the manifest states it.
- **Guardrail**: calibration compares edit rate under learned vs baseline on the same project (A/B on the decision history); if learned is worse, the UI says so and offers the reset.
This is a required part of the M7 state design (snapshots + toggle) and M10 (compare + reset); M5/M4 hooks must read the toggle.
